## Review and implementation notes

- The previous visual corrections are present: fixed-total copy, no profile email, unknown-location confirmation, Kokani open/closed control, unclipped dish-editor controls, owner access wording, current outstanding-cash labels and the web deletion state sequence.
- Screen follow-up: both customer `09 Add address.pdf` files show the PIN code in the area label but lack the editable PIN-code field required by #48. Add that field and its six-digit validation; keep the saved pin and verified delivery polygon authoritative. The source screens are retained unchanged here.
- #62 still needs its SMS fallback/requested-channel and SMS-sent states, including generic owner wording, before that feature is approved. It does not block the current WhatsApp-only scope.
- Shared lifecycle primitives belong to #51 before optional #52. The membership display-name/history snapshot prerequisites must land with #53’s initial backend work before its order screens, with #59 reusing them. These are issue clarifications, not implemented changes.
- Profile/Leave links in final screens describe the completed feature set. Hide Leave until #52 ships and when the account is not linked to both restaurants. Reuse the provided blocked/processing/retry deletion states in-app as appropriate.
- Prices, phone numbers, customer names, order counts and food illustrations are design examples. Configure real business data before release and do not present illustrations as actual restaurant food.
- Native/web interaction, accessibility, responsive layouts and device behavior remain implementation validation tasks. A static reference is not a tested app.
