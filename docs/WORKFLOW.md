# Delivery workflow

1. Open an issue before starting work. Features need acceptance criteria and the exact `approved` label from an authorized maintainer before work begins. A `feature/` branch or an issue labeled `feature` or `enhancement` requires approval, including when a feature issue uses a `bug` or `release` branch.
2. A bug without `approved` needs an `Assessment` section containing exactly `small` or `understood`. For `small`, explain the scope in the `Small blast radius` section. For `understood`, describe both reproduction and impacts in their sections. Placeholder answers are rejected. Unknown classification or an unclear bug requires `approved`. The gate checks structure and common placeholders, not the quality or truth of the assessment; reviewers must assess it. Approval authority belongs to the repository's authorized maintainers.
3. Create a branch named `(feature|bug|release)/<scope>-<issue-number>-<short-desc>`, using lowercase letters, digits and hyphen-separated description words. The positive issue number has no leading zero. Allowed scopes are `ammu-sammu-customer`, `ammu-sammu-admin`, `konkan-fine-dine-customer`, `konkan-fine-dine-admin`, and `monorepo`. A release branch does not bypass feature approval.
4. Open a PR against the default branch with exactly one `Issue: #N` line, or `Issue: https://github.com/OWNER/REPO/issues/N` with the same repository. The linked issue must exist, be open, and match the branch number. Complete summary, validation, file count, and any useful handoff or decisions. Leave PRs open for owner review; do not automatically merge.
5. Keep each PR to at most 15 reviewable files. Additions, modifications, deletions and renames count. A rename counts if either path is reviewable. Only `.gitignore`, `README`, `README.md`, `README.rst`, `README.txt`, and the following exact generated lockfile basenames are excluded: `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `Cargo.lock`, `Pipfile.lock`, `poetry.lock`, `uv.lock`, `Gemfile.lock`, `composer.lock`, `go.sum`. Other generated files, documentation, configuration, tests and workflows count.

The `Delivery policy` check reads live issue and PR metadata, paginates file lists, and fails when data is incomplete. It reevaluates PRs on opening, editing (including base changes), synchronization, reopening and ready-for-review, and on issue label, body or state changes, deletion, and transfer, and default-branch pushes. Each event reevaluates all open PRs; every open PR must have a distinct head commit because GitHub checks are attached to commits. The privileged workflow checks out only the trusted base and does not run PR code. Policy tests run separately with read-only permissions. A check cannot prove work was actually delayed until approval; maintainers must enforce that process.

Workflows introduced by a PR only become effective after merge into the default branch. After merging, a repository administrator must configure a branch protection rule or ruleset to require the `Delivery policy` check and CODEOWNERS review, and restrict who can bypass it. These settings are separate from this repository's files. A check name alone can be spoofed by another same-repository workflow; restrict who can change workflows and policy, and configure the required check's source where GitHub supports it. Pinning the check source to GitHub Actions still allows another workflow from that same app to emit the same check name. Stronger enforcement requires a supported ruleset-required workflow or an independently identified policy app. CODEOWNERS requests review but does not itself enforce approval. The workflow checks for stale state before publishing, but API updates and check publication are not atomic; a subsequent event reevaluates changes, and maintainers should rerun the workflow if a race or API failure prevents publication. A GitHub API outage can prevent creation or completion of a check, so remote failure cannot always be guaranteed; an in-progress check remains pending if completion fails.

GitHub does not allow a PR author to approve their own PR. Before requiring CODEOWNERS
approval, arrange a distinct eligible reviewer: if the connector authors PRs as the sole
owner, that owner cannot supply the required review. Agent review reports do not satisfy
GitHub's human-review requirement. If GitHub cannot list PRs or accept check updates, a
previous successful check may remain visible; do not treat the automation as proof of
approval or as a substitute for merge protections and owner review.
