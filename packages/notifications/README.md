# Notifications and analytics

This package defaults to no collection and no push registration. Firebase configuration is public client configuration (for example `EXPO_PUBLIC_FIREBASE_*`); never embed service-account keys or server credentials. Call `createAnalytics(createWebAnalytics(config), { brand, audience })` and explicitly call `setConsent(true)` only after consent; call `setConsent(false)` on withdrawal. Persist the user's decision in the application and initialize it as off until that decision is known. Only named events and the two constrained dimensions are accepted. Google Analytics is initialized only after consent, with automatic page views disabled and URL/referrer/title values sanitized; withdrawal disables collection and makes a best effort to remove `_ga` cookies. The analytics UI should report initialization failures and must not block ordering.

For web push, supply the public Firebase config and public web push VAPID key to `createWebMessaging`. Bundle the worker into each application's own public directory, e.g. from the repository root:

```
npm run build:worker -w @market/notifications -- --outfile=../../apps/example/public/firebase-messaging-worker.js
```

The destination directory must exist. Deploy the worker under the app's same-origin path and pass its URL and app scope (ending in `/`) to the adapter. Serve over HTTPS or localhost, with browser permission and a Firebase project configured for web push. The worker receives only public config in its URL. The server must send data-only hints with no private content; Firebase can itself display a provider-supplied notification payload before the worker callback runs. The worker displays a generic message and never fetches URLs from payloads. Foreground `onHint` callbacks contain no message data and should refresh authenticated realtime state.

Use `createMessaging(port, backend)` and call `enable(userId)` directly from a signed-in user's opt-in click. Its result reports unavailable, denied, or error states for the UI. Backend callbacks must authorize the current session using RLS and ensure token uniqueness and reassignment; the passed user ID is not authentication. Call and await `disable()` before sign-out or switching users so the old session can delete its token. Retrying after a backend deletion failure is required before signing out. The controller retains its current registration only in memory: the application/backend must separately track this device registration across reloads and remove it on logout, including logout in another tab, expired sessions and other devices. Do not claim reliable logout cleanup until that integration exists.

Native push is intentionally unavailable via `unavailableNativeMessaging()`. Expo Go does not supply the Firebase native provider integration. Supporting iOS/Android requires a custom Expo development build, native Firebase messaging integration and native Firebase project files, APNs setup for iOS, Android Firebase configuration, and verified permission/token lifecycle behavior. No native provider setup or delivery is included here.
