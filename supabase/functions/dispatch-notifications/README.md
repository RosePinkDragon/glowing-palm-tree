This function sends generic data-only refresh hints; it does not establish delivery, grant access, or include order details. Clients must fetch data through authenticated APIs. Session deletion removes bound tokens; existing unbound tokens are never dispatched. Tokens are opaque capabilities and do not prove device ownership.

Deployment requires a Firebase service account with FCM access, `FCM_SERVICE_ACCOUNT` (JSON with project_id, client_email, private_key), `NOTIFICATION_DISPATCH_SECRET` (at least 32 characters), and Supabase service credentials in server-only secrets. Configure a trusted scheduler to POST with `Authorization: Bearer <secret>`. No scheduler, credentials, or production deployment are configured here. Provider setup and real delivery remain unverified. `verify_jwt` is disabled for this function only because it checks the scheduler secret before claiming jobs.

Customer notification taps use the service-only `notification_delivery` RPC, which wraps the existing lease/session/business/recipient checks and returns only the destination token and an opaque customer order UUID. The worker uses that UUID only for a fixed same-origin `/orders/<id>` route; opening still requires authentication and current order access. Admin payloads remain generic. Apply the routing migration before deploying this dispatcher version.
